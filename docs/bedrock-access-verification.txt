3. Quota increases requested, values, and reasoning
================================================================

I requested no quota increases, because every quota the Lab 3 workload touches
is already non-zero and far above what the workload needs. My estimate: the
corpus is about 4,000 words, roughly 5,300 tokens at ~1.3 tokens per word, split
into a few dozen chunks. One full re-embedding is therefore a few dozen requests
and ~5,300 tokens, which is under 2% of the Titan limit of 300,000 tokens per
minute and under 1% of 6,000 requests per minute, so even re-embedding several
times in the same minute fits. For generation, a RAGAS evaluation run is a few
hundred Haiku calls; at roughly 2,000 tokens per call (retrieved context plus
prompt plus a short answer), 300 calls is about 600,000 tokens. Even if all of
them landed in a single minute, that is 12% of the 5,000,000 tokens-per-minute
limit and 3% of the 10,000 requests-per-minute limit. At 30x that load (about
9,000 calls and 18 million tokens) the request rate would still fit in one
minute but the token rate would not, so the run would need to be spread over at
least four minutes or a token-per-minute increase requested; that is the point
at which an increase becomes defensible, and the Lab 3 workload is nowhere near
it. The Titan quotas are also marked not adjustable, so a request through
Service Quotas would not have been accepted for them in any case. I chose the
us. inference profile over global. so that inference stays inside US regions,
which is the appropriate default for a retailer handling US customer data.
